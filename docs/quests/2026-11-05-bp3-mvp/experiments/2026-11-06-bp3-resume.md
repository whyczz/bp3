# Exp 9 — bp3-resume: Quest workspace recovery and Controller resume

## TL;DR

Provide **`bp3-resume`** to recover an existing Quest workspace, including when
the human resumed Pi outside Zellij. Reattach what is alive; hand off the exact
Controller conversation when requested; reconstruct only what is safely known
to be gone. Do not replay the original task or launch duplicate Controllers.

Status: **proposed follow-up, not implemented**. The human requested a later exp
and explicitly named `bp3-resume`, allowing a CLI or skill. Recommend a
deterministic CLI with an optional thin skill wrapper, not model-driven process
recovery. Default scheduling is after Exp 3; this does not expand MVP acceptance,
Exp 2 fixes or the active Exp 7.1 assignment. No launch/commit/promotion authority
is granted by this record.

ELI5: restore the workspace, not replay the mission. Resuming a notebook does not
put its desk, windows and coworkers back where they were.

## Triggering observation — not acceptance

On 2026-11-06, at home checkpoint `e442374`, the human reported losing Zellij and
resumed this Pi conversation in a standalone Ghostty terminal. Fresh checks found:

- `ZELLIJ`, `ZELLIJ_SESSION_NAME`, `BP3_SESSION` and `BP3_QUEST_FILE` were unset.
  Pi supplied an explicit current session file/ID; process ancestry placed it
  under the standalone shell/Ghostty, not a Zellij terminal.
- `zellij list-sessions --no-formatting` still listed
  `bp3-bp3-mvp-0100a83fd2` as live, not EXITED. Structured metadata showed the
  Controller, prior reviewer, Exp 7 author and one other terminal, with an
  attached client. That is not proof of human visibility or model idleness.
- The workspace's saved Controller session and this resumed conversation have
  different IDs/storage locations. Attaching the old workspace alone does not
  move or replace the current conversation. “Pick the latest session” is unsafe.
- Explicit reattach in a new Ghostty window, with `--window-save-state=never`,
  increased attached clients from 1 to 2. The four terminal identities and exit
  flags were unchanged. No Pi/Worker/runtime was launched or restarted. This
  established attachment, not a completed conversation handoff.
- The human then saw a nested-session warning in the new window. Both clients
  were focused on fullscreen `Tab #5`, whose recorded command was
  `zellij a bp3-mvp`. Stable-tab-ID focus moved client 1 to Controller but left
  new client 2 on `Tab #5`; a pane-ID-scoped attempt also failed to move client 2.
  The verified local shortcut, Ctrl+T then 1 (Ctrl+G first if locked), was supplied
  for that window. Its visual outcome is not yet confirmed. Recovery must target
  the intended attachment, not count any client/Controller focus as success.

The cause of the original lost display is not established; the server was not
lost at inspection. The proven product gap is recovery/binding after Pi resume,
not evidence that a running terminal process can be teleported into Zellij.

## Existing behavior, scope and dependencies

[`scripts/zellij-init.mjs`](../../../scripts/zellij-init.mjs) creates a private
workspace reservation, a new Controller with an initial `@prompt.md`, and a
Ghostty attachment. It intentionally refuses existing live/resurrectable sessions
and reservations. Its private Controller script sets `BP3_SESSION` and
`BP3_QUEST_FILE`; ordinary Pi resume outside that script does not restore them.
[`tests/workspace.test.mjs`](../../../tests/workspace.test.mjs) tests refusal and
initialization, not recovery. Preserve those protections; do not delete the
reservation or rerun its startup script to force a resume.

Installed Pi's `sessions.md` documents exact `--session` selection and the saved
session cwd. It restores conversation history, not bp3's desktop/Board binding.
A shell command cannot change the environment of the already-running parent Pi.

In: same-machine recovery of an existing registered Quest workspace, explicit
Controller-session selection/handoff, restored environment binding, safe retries
and diagnostics. Initial desktop support may remain macOS/Ghostty/Zellij.
Out: portable full restore, implicit runtime/build activation, new assignments,
automatic Worker resurrection, process migration, transcript rewriting, polling
with model calls, broader concurrency or generalized consumer onboarding.

Reuse the workspace binding and Exp 2's mounted-identity/safety contracts.
[Exp 4](2026-11-06-controller-wait-notify.md) owns notification/decision-wake
policy, not desktop recovery. [Exp 8](2026-11-06-worker-retirement-revival.md)
owns Worker revival with new authority; this exp must not resume expired Worker
sessions as a shortcut. Reattachment itself does not require that revival feature.

## Mini-design and responsibility map

Proposed entrypoint, **not a command available today**:

```text
bp3-resume [QUEST] [--pi-session PATH] [--inspect]
```

Exact flags are implementer design work; the human-facing name is `bp3-resume`.
Without an explicit selector, choose only a uniquely validated workspace/session
binding. Otherwise list choices and stop; neither cwd nor most-recent history
alone is authority. `--inspect` must have no launch, window or Board side effects.
A skill, if added, calls the same CLI rather than maintaining a second algorithm.

```text
resolve existing Quest + workspace + selected Pi session
                         |
                 inspect current ownership
                  /          |           
         live workspace   handoff needed   dead/ambiguous workspace
               |               |                    |
          attach only     stop/resume one       reconstruct safe UI
                          exact conversation    OR explain the hold
```

1. **Resolve and inspect.** Use private workspace metadata to bind repository,
   Quest, Zellij identity/incarnation and exact Controller session file/ID/cwd.
   Include existing Board/runtime references when present; report absent or
   conflicting references instead of inventing them. Use public Board operations,
   documented Pi/session metadata and structured terminal/process observations,
   never pane text. Keep metadata private and omit credentials from output/argv.
2. **Attach, do not initialize.** If the intended workspace/Controller is alive,
   attach or focus its owned client, verifying that the intended attachment
   reaches the Controller tab. With multiple clients, changing the first client's
   focus is not success for a newly opened window. Inside an already-bound Zellij
   session, navigate rather than start a nested attach. Never force nesting to
   dismiss a warning. Repeated requests must not multiply windows, tabs or Pi
   processes. Retain Ghostty's per-instance restoration suppression;
   do not change global settings or resurrect every saved window. An existing
   Controller with a different conversation requires an explicit choice, not
   silent replacement.
3. **Handoff this conversation explicitly.** A Pi already running outside Zellij
   cannot be rebound by exporting variables in a tool subprocess. Establish a
   graceful, explicit handoff: finish/stop the old owner before starting the
   exact selected session in a mounted Controller tab with the correct cwd,
   `BP3_SESSION`, `BP3_QUEST_FILE` and Controller instructions. Never run two
   managed Pi writers on one session file. No guessed PID kill, automatic fork,
   generic `--continue`, initial task argument or replayed inbox message. If
   ownership cannot be proved, explain the hold and next action rather than spawn.
4. **Recover a dead workspace conservatively.** Detect EXITED, missing, stale and
   ambiguous identities separately from a lost client. Inspect saved launch
   commands before any resurrection; do not use `--force-run-commands` or replay
   the original prompt/Worker launch files. Recreate only the authorized UI and
   Controller under a new recorded incarnation. Preserve Board/runtime, frozen
   artifacts, worktrees, histories and obligations. Missing Worker terminals are
   reported honestly; their authority is not restored by reusing names/pane IDs.
5. **Verify and reconcile.** Use exact mounted-pane/session/cwd/environment facts,
   not merely an accepted window request or stored title. Claim only the layer
   recovered: attachment, Controller handoff or missing components still held.
   Retain enough private request progress to inspect an interrupted attach/spawn;
   retries must not blindly repeat it. Recovery neither resumes model work nor
   renews budgets/leases without the existing work authorization path.

Local ownership is a cooperative guard, not hostile same-user isolation. A stale
PID or absence of an open file descriptor does not prove a session has no writer.
Read the installed Pi CLI/session docs and actual callers before implementing
handoff; any extension component also requires its relevant docs/examples and
real-host tests. Do not assume resuming an incomplete conversation is inert.

## Acceptance and evidence

The manual reattach above is an observation, **not acceptance of `bp3-resume`**.
All new command/skill behavior below is unimplemented and unrun.

1. Lose only the desktop client: `bp3-resume` restores access to the same live
   workspace with unchanged Controller/Worker identities and no initial-prompt
   replay, extra model request, runtime restart or new Run. Repeating it does not
   multiply windows; inspect mode has no side effects. With two attached clients
   and a fullscreen nested-command tab, target the correct client's Controller
   view. Existing unrelated clients/focus must not be mistaken for recovery.
2. Resume Pi outside Zellij as in this report. Explicitly hand off that exact
   conversation once, preserving history and cwd, restoring verified Quest/session
   binding and leaving no concurrent managed writer. A live different Controller
   or ambiguous session selection refuses silent takeover.
3. Kill a disposable Zellij session, then recover. Commands embedded in its saved
   layout cannot automatically replay work. Recover the permitted Controller/UI
   or expose a specific hold; retain evidence and report missing/orphaned Workers
   without resurrecting their authority. Existing runtimes are not hot-upgraded.
4. Duplicate/concurrent requests and failure before/after window creation, owner
   handoff and new Pi startup converge or hold without duplicate effects. Reused
   session names/PIDs/pane IDs, missing/changed session files, wrong cwd/repo/Board
   and stale reservations cannot select an unrelated workspace or history.
5. Startup is held for human/workflow input: no recovery-attributable provider
   requests, including accidental continuation of unfinished model/tool work.
   Measure separately from legitimate existing Worker traffic. No pane typing,
   transcript rewriting, secret-bearing output or history deletion is required.
6. An authorized visible rehearsal confirms the recovered Controller and Workers
   are actually watchable. Structured metadata is supporting evidence, not a
   replacement for that observation. Preserve unrelated tabs/windows/sessions,
   Git refs, Board obligations and the existing frozen build throughout.

## Red chair, runbook and next step

Strongest attack: “resume” duplicates a live Controller, concurrently writes the
same history, or resurrects a saved command with obsolete authority. Distinguish
attachment from ownership handoff and Worker revival. Refuse ambiguity instead
of turning a harmless missing window into duplicated work.

Today, from a shell outside Zellij and after verifying the exact session is live,
ordinary `zellij attach SESSION` can restore its display. From inside that same
session, navigate to its Controller tab instead of nesting an attach. In the
observed local keymap, Ctrl+T then 1 selects the first tab; Ctrl+G unlocks first
if needed. Attaching/navigating does not move this Pi conversation or restore its
bp3 binding. Do not invoke the initializer again, delete reservations, force-run
saved layouts or start a second copy of the current session as a workaround.

Next: after reprioritization/prerequisites, pin the minimal `bp3-resume` interface,
private binding and single-owner handoff mechanism. Start with provider-free
fixtures around the existing helper, then real installed-Pi resume tests and an
explicit visible rehearsal. No current Worker assignment is amended by this plan.
