# bp3 lint: rule engine for OCaml and the CLI surface

## Context

Frozen 2026-11-15 in red-ink round 1 (Output) on
[bp3-unit-tests](../quests/2026-11-14-bp3-unit-tests/GOAL.md),
when the owner called **B: split Exp 3 out**. The quest
titled "unit tests" was emitting three things — a unit
layer, a framing standard, and this: a SonarQube-shaped
lint engine whose error-severity findings gate
`make check` for every future change. A new gate with its
own failure surface does not ride as a passenger on a
testing quest. Full sketch at freeze time:
`experiments/exp-3-linters/EXPERIMENT.md` in that quest
folder (demo trace: JSON findings such as
`ocaml/no-legacy-spelling`, exit 1 on any error finding).

## Sketch

- `bp3 lint` classifies tracked files by language
  (OCaml first) and surface (the bp3 CLI), runs rule
  packs, emits findings as JSON (tree format for humans).
- A rule is data, never prose in a skill: id, severity,
  pack (`ocaml` | `cli`), checker (command | pattern),
  message.
- `make check` gates on error-severity findings.
- Deliberately does not add: other languages' packs
  (shell/JS keep shellcheck / `node --check`), prose
  style guides, auto-fix.

## Blockers

- No rule has actually been demanded yet; the two demo
  rules are illustrative, not requested.
- Exp 2 of bp3-unit-tests was its stated dependency
  (the engine's seams join the unit suite); that quest
  now lands without it, so the dependency needs
  re-deciding at thaw.
- Severity/gate semantics (what blocks landing vs warns)
  unreviewed — exactly the review this split buys time
  for.

## Promotion trigger

Thaw when a concrete, machine-checkable sin recurs by
hand a second time — a legacy spelling, a verb missing
from usage text — and someone wishes a rule had caught
it. First move on thaw is `/quest` transcription, with
the gate semantics as its first design question.
