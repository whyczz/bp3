# Exp 2 — Auto-land implementation contract

Status: proposed implementation packet; not an implemented guarantee.
Governing scope: [MVP Quest, Exp 2](../quests/2026-11-05-bp3-mvp.md).
Genesis evidence: [Exp 1 record](2026-11-05-genesis.md). No master promotion or push authority.

## TL;DR

**Run → Run Outputs → Review → land → cleanup.** Independent checks and a fresh
reviewer must approve the exact commit. Land is fast-forward only onto the
registered consumer's Quest branch; no merge, cherry-pick or automatic rebase.
Git owns the actual integrated code. The Board owns assignments, approval
evidence and outstanding work, and reconciles its landing projection from Git.
No distributed two-phase commit or standalone Integration Intent is required.

An exact, already-present approved commit may count as **observed integration**,
even without proof that bp3 moved the ref. Conflicting authority or unexpected
movement stops recovery; it never becomes a new base. Once the land report is
recorded, the runtime retires the exp's Workers. Human takeover holds closure
until `/bp3-release`. The full loop must also work in an external consumer repo.

## Context and bootstrap boundary

This plan renames **Execution → Run** and **Candidate → Run Outputs**. A code
Run's Outputs include one exact commit plus evidence; the plural does not add
multi-commit selection or new artifact kinds. The rename is applied in the
codebase as schema v2: tables `runs`/`run_outputs`, `run_id` fields, `BP3_RUN`,
`Run_ops`, and context keys `runs`/`run_outputs`. `bp3 migrate` performs the
rename-only v1-to-v2 migration (runtime stopped, `.v1-backup` kept); new Boards
init at v2 and v1 Boards refuse normal opens. No Exp 2 behavior (roles, checks,
reviews, lands) is added by the rename. Historical Exp 1 evidence is not
rewritten to pretend that the new model already exists.

Current `Workflow.report` records outputs, not approval. `Authority.allowed`
has no reviewer role. `Run_ops.reserve` permits only generation zero,
`Store.schema` has one live-run slot, and `Launcher.launch` refuses unrecorded
target movement. These are genesis limits, not APIs to bypass with direct SQL.

Bootstrap history (skill fix on `master`, Exp 1 checkpoint on `quest/bp3-mvp`,
follow-up checkpoints) lives in the [genesis record](2026-11-05-genesis.md) and
git; none of it is auto-land, master promotion or push authorization. Before
delegation: record the exact clean Quest commit with the final plan, preserve
the old bootstrap Board, and establish a fresh implementation Board there.
Never silently rewrite an existing Board's frozen base or substitute a dirty
checkout.

Delegate the kernel work through the frozen genesis runtime. Test the next
kernel on Board copies and fresh toy repos; do not hot-swap the coordinator
running the implementation exp. Toy auto-land is not acceptance or activation
of the kernel that implements it.

## Architecture and data

```text
frozen brief -> author Run -> immutable Run Outputs
                                      |
                       Review: independent checks
                         + fresh reviewer Run
                                      |
                         conditional Git ref update
                         OR observe exact approved tip
                                      |
                        recorded land report + cleanup
```

The standard/code-only, single-host, cooperative trust model remains. One author
and one reviewer maximum; sequential is sufficient. No general DAG, new lanes,
external push, master promotion, hostile-code sandbox or autonomous rebase.

### Concepts and evidence

| Concept | Required facts |
|---|---|
| Quest / exp | Registered consumer repo and Quest target, frozen brief/base, selected Run Outputs, explicit amendments/cancellation and unresolved obligations. |
| Run | Runtime-assigned author/reviewer role, ownership generation, workspace, pi session/endpoint, work authority and lifecycle observations. A reviewer is a different Run/session/worktree from the author. |
| Run Outputs | Immutable submission bound to its Run and brief. Code outputs name an exact commit descending from the frozen base, with Worker evidence kept distinct from independent checks. |
| Review | Exact outputs/commit/base/brief; runtime-produced independent check evidence; fresh reviewer identity, accept/reject and findings. Checks and judgment share one view, not one writer's authority. |
| Land report | One durable report per accepted integration: repo/target, before/after commits, outputs/review references, observation basis, TL;DR, IIUC, demos, tests, code pointers and revert handle. Retained after rework or revert. |

Review's check evidence includes frozen argv, independent workspace identity,
exit status, retained stdout/stderr, clean HEAD/tree observations and time.
Worker prose cannot create a successful check result; an author credential
cannot write the reviewer verdict. Concrete tables are pinned in
[Schema v3](#schema-v3-and-operation-homes-pinned-design); the rows above are
responsibilities, not a requirement for one state machine per concept.

Keep runtime bookkeeping private (receipts, cleanup queue, interaction
revisions, errors, binary/bridge fingerprints) and inspectable, without making
it a planning object: a hold/error explains a block; it is not a new exp phase.

### Fewer states, separate facts

- Derive labels such as awaiting review, ready to land and held by human from
  outputs, Review and current obligations; do not maintain parallel transition
  ladders that can contradict those facts.
- Use **landed** as the integration outcome/projection, not `auto_landed` as
  proof of which actor moved Git. Automatic operation and observed integration
  are evidence distinctions in the report, not separate exp lifecycles.
- Reporting seals author work; review completion seals reviewer work. A sealed
  Run cannot submit new work or regain authority through a heartbeat. Its visible
  session may still exist for inspection, release and eventual cleanup.
- Rejection keeps the same exp and creates a fresh author Run/generation. Old
  outputs and reviews stay immutable; replay cannot reselect obsolete outputs.
- Do not force work authority, terminal presence, idle, takeover and permission
  into one enum. They answer different questions even when the UI is simple.

Starting a reviewer is not author rework. Generations are per exp, monotonic
across roles: every reserve takes `exps.generation + 1` and updates the exp, so
the existing `live` equality check fences all older Runs. Concretely:

### Schema v3 and operation homes (pinned design)

Rename-only schema v2 is applied. Exp 2 adds schema v3, migration `bp3 migrate`
v2-to-v3 under the same rules (runtime stopped, backup kept, old binaries
reject v3):

- `quests` gains `expected_head`, initialised to `base`. The land transaction
  advances it; `Launcher.launch` refuses when the actual target differs from
  `expected_head` instead of the frozen `base`, so later exps in a Quest can
  launch after a land.
- `runs` gains `role` (`author|reviewer`) and `interaction_revision` (integer,
  bumped by the bridge on takeover and interactive input). `desired` lifecycle:
  `run → sealed` on report or verdict, `sealed → superseded` when newer outputs
  arrive for the exp, `→ retired` when cleanup completes; `cancel`/`expired`
  unchanged. Drop the Board-global `one_live_run` index; add
  `UNIQUE(exp_id, role) WHERE desired IN ('run','sealed')` — one active author
  and one active reviewer per exp.
- `run_outputs` gains `superseded`, set in the transaction that records newer
  outputs for the exp. Obsolete outputs and their reviews stay readable.
- `check_runs(id, run_output_id, argv, worktree, exit_status, interrupted,
  stdout_path, stderr_path, head_before, head_after, tree_clean, started_at,
  finished_at)`. Pass means exit 0, HEAD/tree unchanged, not interrupted. Only
  the check operation writes this table; no Worker credential can.
- `reviews(id, run_output_id UNIQUE, reviewer_run_id, verdict, findings,
  created_at)`. **An accepted review row is the selection**; there is no
  separate selected-outputs field. Role is read from the reviewer Run's row,
  never from the caller type, so an author credential cannot write a verdict.
- `land_reports(id, integration_key UNIQUE as exp:run_output, quest_id, repo,
  target_ref, before_sha, after_sha, basis cas|observed, review_id, tldr, iiuc,
  demos, code_pointers, revert_sha, recorded_at)`. The runtime composes the
  report from stored check/review/output facts; no model call. `revert_sha`
  is null until an explicit revert persists its undo commit, and not
  applicable when `after_sha = before_sha`.
- `cleanup_queue(id, run_id UNIQUE, land_id, state
  pending|held|closing|done|error, interaction_revision, detail, queued_at,
  updated_at)`. One entry per Run, enqueued in the land transaction and
  drained oldest-first by the runtime loop. Entries are retained with their
  final state as the cleanup record; done entries are never re-drained, and
  the queue is work to do, not a planning object.

Operation homes (one writer per external effect):

| Operation | Caller / home | Effect |
|---|---|---|
| check | Controller CLI op, deterministic code | independent worktree at C, `Process.run_bounded`, one `check_runs` row |
| reviewer launch | runtime reserve with `role=reviewer` | worktree detached at C, brief budget reused (`max_seconds`) |
| verdict | reviewer Run op (`review`) | one `reviews` row; seals the reviewer |
| land / observe | runtime reconcile tick, no external op | Git CAS or exact-C record, `land_reports`, `expected_head`, `cleanup_queue` entries |
| revert | Controller CLI op | undo commit in a detached worktree, CAS, `revert_sha` |
| lifecycle signals | bridge, token+generation+session fenced | exempt from `desired`/deadline so sealed or expired Runs can still release/settle/exit |

`bp3 context` exposes `check_runs`, `reviews`, `land_reports` and pending
`cleanup_queue` entries alongside the existing projections, so a replacement
Controller sees land state without reading panes or raw SQL.

## Source of truth and landing recovery

**Git is authoritative for actual refs and code.** During an active Quest this
means its registered Quest branch; `master` is the later promotion destination,
not a substitute for the in-progress Quest. The Board retains the expected base,
selected outputs, approvals and obligations. Those are authority/precondition
facts, not a competing claim about the current Git tip.

The Board may temporarily lag Git after a crash. Reconcile its outcome and
report instead of requiring an atomic transaction spanning SQLite and Git.
There is no standalone Integration Intent or `prepared/applied/finalized`
workflow for ordinary landing.

### Exact-tip rule

For selected Run Outputs at commit **C** and their frozen expected base **B**,
resolve the actual target through the same Board/Quest/consumer binding:

| Actual target | Action |
|---|---|
| **C** | If those exact outputs, Review and selection remain valid and unconflicted, reconcile the outcome as landed. No Git mutation is needed. |
| **B**, different from C | With valid Review and current authorization, attempt `git update-ref TARGET C B`. A failed compare-and-swap is not permission to substitute a new base. |
| Anything else | Record actual/expected target and the blocking reason; stop automatic integration. |

Approval must already be durably recorded before bp3 attempts the Git update.
This is an exact-tip recovery rule for a not-yet-recorded outcome, not “C occurs
somewhere in history, therefore it landed.” Later known lands and explicit
reverts retain earlier reports and advance the recorded expected head. An
ancestor match, equivalent tree, reverted change or arbitrary descendant cannot
fill a missing report. If `C = B`, describe the unchanged tip honestly rather
than claim a new ref movement; the outputs still require valid Review.

**Intentional policy change:** an external move to exactly C may be accepted as
observed integration when the recorded outputs and approval qualify. Absence of
a bp3 intent record alone is no longer an incident. This relaxes provenance,
not code/repo/review binding. Record when integration was observed; do not invent
the time, actor or command that moved the ref. Record a bp3-performed update only
when its successful result is actually known; otherwise use observed integration.

A matching Git tip never cancels a cancellation, superseded selection, rejected
review, recorded revert or conflicting amendment. Preserve the actual Git observation but stop
acceptance/cleanup for that unresolved case. Do not promise automatic resolution
of authorization changes racing with a crash. Human takeover cannot erase a
known Git fact; it still prevents new autonomous mutation and holds closure.

## Consumer repository binding and transfer gate

Existing `quests.repo` is the starting point. Bind Runs, Outputs, Review and
reports through that registered consumer; foreign keys are sufficient. Validate
worktree membership with Git repository metadata, not a path prefix or SHA.
Canonical filesystem aliases share a binding; a separate clone/fork does not,
even when commits and target-ref names match. No global repo registry is needed.

The desktop initializer and skill installer still derive their project root
from bp3. Generalized consumer onboarding is separate work. This gate uses the
real CLI/runtime, explicit fixture Board, consumer repo and owned Zellij session,
not direct SQL or Git shortcuts around the integration API.

```text
frozen bp3 build -> Board / Quest -> external consumer A
                                  author / checks / reviewer
                                  land -> cleanup -> explicit revert

consumer B may share A's commits/ref names, but not its authority
```

- Put A, its Board and owned Run/check workspaces outside both the bp3 checkout
  and bp3's `.bp3/`. A's Quest/exp documents stay in A. Fixtures are defined in
  bp3's tests; they do not become a real esc3 Quest or modify esc3.
- Resolve checks, review, integration, replay/recovery and revert through the
  same Board/Quest/Outputs/consumer chain. A foreign receipt or colliding local
  ID cannot substitute, including in the exact-C observation path.
- Run a frozen non-Dune checker with explicit cwd/repository assertions in A's
  independent verification worktree. Invoke the CLI from bp3 and an unrelated
  cwd; restart the runtime elsewhere. Never infer the consumer from the caller's
  cwd, executable location or Git remote URL.
- Compare bp3 refs/tracked source and frozen binary/bridge fingerprints before
  and after. A alone receives intended land/revert; B's target, unrelated sessions
  and the Controller remain untouched. This is cooperative repository-boundary
  testing, not hostile-process isolation or cross-repo atomic landing.

## Operations and authority

1. **Check Run Outputs.** Read the sealed submission and immutable brief; verify
   repo/base/commit bindings and create an independent worktree at that commit.
   Run frozen argv directly, without shell interpolation, outside SQLite
   transactions, via `Process.run_bounded` with the brief's `max_seconds` as
   the deadline. Retain output outside the checked
   tree. HEAD and tracked/untracked source must remain exact; ignored build
   artifacts are allowed. Retain failures/interruption honestly, never a passing
   check receipt for an interrupted process.
2. **Review.** Launch a fresh reviewer Run bound to the exact outputs. Supply
   brief, diff and independent check evidence. Record accept/reject and findings
   through role-authorized Board ops. Both successful checks and an accepting
   reviewer are required; combining their presentation does not weaken either.
3. **Rework.** Rejection creates another author Run on the same exp using the
   rejected outputs/findings. Scope/check changes require recorded amendments,
   not interpretation of steering prose. Fixtures freeze their commands before
   launch: `dune runtest --root .` for the original toy and the non-Dune checker
   for the external consumer. Old approval cannot authorize amended work.
4. **Land or observe.** Runtime applies the exact-tip rule, not an author command
   or another human scheduling step. Validate current selection, Review,
   repo/target and acceptance obligations. Cancellation/rework conflicts block;
   takeover/permission holds block a new autonomous Git mutation. Work budgets
   bound active Runs and checks; expiry of a completed author's lease alone
   does not invalidate immutable outputs or Review. Never mutate master or a
   non-Quest ref. Before mutation, refuse a target checked out in any worktree.
   Serialization is structural: only the singleton runtime mutates Git, on
   its reconcile tick; Board authority changes are short `BEGIN IMMEDIATE`
   transactions, and the recording transaction revalidates selection and
   approval after any CAS. Git CAS alone does not serialize Board
   cancellation. If authority consistency cannot be established after a
   crash, stop instead of retroactively inventing permission.
5. **Record and clean up.** After successful CAS or qualifying exact-C observation,
   transactionally record the landed projection, expected Quest head, one land
   report/event and durable `cleanup_queue` entries for owned author/reviewer Runs.
   Revalidate selection/approval before recording; a conflict after Git moved
   remains visible and prevents automatic cleanup. Use a stable integration key
   bound to the exp/selected outputs/review, so concurrent/retried observations
   do not duplicate reports or cleanup. No SQLite transaction spans a process
   call. Runtime cleanup follows the Board transaction; failure does not undo Git.
6. **Revert explicitly.** A Controller request binds the original land, consumer
   target and exact expected current head. Create a new commit undoing that
   land's change in an owned worktree; do not reset or rewrite history. Persist
   the constructed revert SHA with the ordinary request metadata before target
   mutation, so retries know which undo was authorized rather than minting a
   different commit. CAS to that SHA and reconcile the exact result; conflicts,
   changed requests or unexpected targets stop. Keep the original report and
   revert receipt, and record the reverted disposition. The toy intentionally
   returns to a failing baseline: undo is not a newly accepted feature and needs
   no invented green Review. This explicit undo request is not a general
   Integration Intent lifecycle. Master rollback/build activation remains Exp 3.

Controller death does not transfer Run ownership. A replacement reads the Board
and Git, resumes eligible work and reconciles outcomes. The same operation ID
replays the same result; changed input conflicts. Historical report receipts do
not grant current work authority, including genesis's cached-offer fencing.

## Post-land Worker retirement and human release

**Policy owner:** Board operations decide eligibility and persist cleanup work;
the runtime performs/reconciles shutdown without a model call or live Controller.
The existing bridge protects local interaction and may request graceful pi
shutdown. No separate extension infers completion from terminal text.

### Trigger and authority

- Trigger only after an accepted exp-to-Quest outcome and its report are recorded,
  whether from known CAS success or qualifying observed integration. Report,
  idle, Git invocation alone and Quest-to-master promotion are not triggers.
  Unresolved integration conflicts cannot initiate successful-retirement cleanup.
- Seal work at report/review completion, while retaining authenticated lifecycle
  signals: presence, settled, takeover/release and shutdown acknowledgement.
  Current `Board.dispatch` gates all bridge signals through `Authority.live`;
  change that explicitly rather than keep `desired=run` or revive work authority
  for cleanup. Expired work budgets must not strand lifecycle-only retirement.
- Cleanup covers owned Runs of the landed exp, including superseded attempts
  still present, not other exps or the Controller. Preserve Outputs, worktrees,
  branches, Board history and pi sessions. Successful retirement is not `cancel`.
  Cancellation/abandonment cleanup remains a separate explicit disposition; do
  not fabricate landing to collect failed or legacy Exp 1 sessions.

### Human handoff: reuse `/bp3-release`

The existing command sends an authenticated `release` signal and requires idle.
Never infer release from pane text or a sentence in a conversation.

1. With no takeover, a safely settled Worker closes after recorded land without
   a human command. Release before land remains sufficient absent new interaction.
2. Interactive input/user shell activity latches takeover. A landed Worker under
   takeover stays open with the reason: waiting for `/bp3-release`.
3. Release clears only that Run's current takeover, not permissions, questions,
   queued input or other obligations. Closure also requires settled-idle and no
   pending input, permission prompt or unresolved obligation. Explicitly dispose
   of obligations rather than silently delete them. Release never reopens work.
4. Bind release/close authorization to the exact Run/session and a monotonic
   interaction revision at both Board and bridge. New interaction invalidates
   previous eligibility. A delayed release response or cached acknowledgement
   cannot clear newer takeover or authorize closure.
5. Recheck local idle/input/takeover/permission at the shutdown boundary and
   serialize it with input handling. Activity before shutdown is committed holds
   closure; afterward the session is closing and accepts no new work. Runtime
   must not bypass a withheld handoff by killing the tab.

### Recoverable, scoped cleanup

Retain stable per-Run `cleanup_queue` entries and progress/errors before external action.
Revalidate exact session incarnation and pane/process ownership; reusable PID or
tab ID alone is insufficient. Request graceful shutdown with a bounded wait
(named constant, default 10 seconds, matching the heartbeat stale window),
then remove only the owned Worker terminal/tab by explicit identity, never focus.
Do not close a tab containing unrelated terminals. Keep the Controller, shared
Zellij session and Ghostty window. An empty terminal does not prove every child
process exited; record only observed completion and disclose unsupported cleanup.

Restart resumes pending cleanup without respawn. Reconcile an already-gone exact
target; ambiguous identity or timeout stays visible as pending/error, never a
reason to guess or force-kill unrelated processes. Human hold is not a timeout.
Cleanup failure preserves the land report and pending work: do not undo Git,
repeat land or drop the request to repair a terminal problem.

## Storage, migration, and compatibility

Schema v2 (rename-only) is applied; `Store.open_db` requires it and directs
v1 Boards to `bp3 migrate`. Exp 2's v3 follows the same pattern: named
migration under exclusive runtime ownership with a consistent backup.
Preserve rows, frozen briefs, receipts, event cursors and terminal
obligations. Test populated Board copies; keep historical evidence and its
frozen runtime untouched. Old binaries must reject v3. The v3 migration does
not migrate live bridge packets; Runs resume only through the frozen runtime
that owns their Board generation.

Store authoritative coordination facts and idempotent receipts; treat landing
status/current-head observations as projections reconciled with Git. Retain
expected heads as preconditions, never silently replace them with observed tips.
A SQLite snapshot alone cannot restore Git repositories, approvals lost outside
that snapshot, or live sessions. Full restore is unproven. Independent worktrees
protect evidence from accidental author edits, not hostile same-user processes.

## Acceptance checks

### Outputs, Review and landing

- Fresh role-bound author/reviewer Runs; the author cannot approve itself or
  write passing independent check evidence. Review binds exact Outputs/brief/base.
- Failed/interrupted checks, source/HEAD changes during a check, wrong bindings
  and rejection never yield a land report, even if Worker prose claims success.
  Rejection creates rework on the same exp; obsolete outputs/reviews stay
  recorded but cannot regain selection by replay.
- Happy path on a fresh toy: checked/reviewed Outputs auto-land once, emit one
  report and a working revert handle, then close owned Workers. Controller and
  evidence survive; no master movement, push or routine human scheduling/closure.
- Exact-C observation: externally advance the fixture target to the selected,
  durably approved C with no bp3 landing record. Reconciliation accepts it once
  as observed integration and does not claim bp3 caused the move. This fault
  injection is not a substitute for exercising the normal land path.
- Unexpected tip, rejected/unreviewed exact C, wrong-repo C, cancelled/superseded
  selection and conflicting amendment refuse acceptance. Ancestor match,
  equivalent tree or reverted history is insufficient. An unchanged approved
  tip is not described as a new Git mutation. No base repair/refreeze, no
  relabeling an ambiguous mutation as authorized.
- Runtime death before CAS, after CAS before the Board write, and after the
  Board write converges to one report/cleanup set when unconflicted. Duplicate
  or concurrent requests never duplicate integration. Authority races either
  serialize or leave an explicit conflict, never a false success. New human
  activity still blocks unsafe mutation or closure.
- A checked-out target refuses ref mutation. Completed author-budget expiry
  does not invalidate sealed Outputs/Review; active budgets remain enforced.
- Explicit revert creates a new commit, restores the fixture baseline tree and
  preserves both records. Retry/crash reuses the recorded undo SHA; conflicts
  and moved targets refuse. No fake passing check is attributed to the undo.

### External-consumer transfer

- Full author/check/review/land/close/revert loop through real ops in demo
  repo A outside bp3. Assert A's records/check cwd and unchanged bp3 refs,
  tracked source and frozen build fingerprints, repo B target, unrelated
  sessions and Controller.
- Invoke the CLI from bp3 and an unrelated cwd; restart the runtime elsewhere.
  Check, exact-tip reconciliation and revert still resolve to A. The fixed
  non-Dune checker must detect an incorrect cwd/repository.
- B holds the same commit SHA and target-ref spelling. Mismatched workspace
  and outputs/check/review bindings across Board/Quest/repo contexts refuse
  without target mutation, including replay, exact-C observation and revert.
  Filesystem aliases still resolve consistently.
- Hand-onboard one throwaway demo repo (not esc3) using only shipped CLI ops:
  pre-create its `refs/heads/quest/*` at the base, register the Quest, run one
  exp to a recorded land. Record the exact commands and elapsed human time as
  the Quest 3 onboarding runbook; esc3 itself is not modified or gated here.

### Retirement and compatibility

- Reported/blocked/awaiting-review Workers and unresolved land conflicts do
  not close. Release without an accepted, recorded land triggers nothing.
- No takeover needs no release. Takeover holds closure; settled-idle release
  permits it only after other gates clear. Pre-land release need not repeat.
  Busy release refuses; permission, queued input and unresolved obligations
  hold closure. Delayed/replayed release or shutdown responses lose to newer
  interaction at both Board and local bridge boundaries.
- Sealed Runs retain lifecycle communication, not new work or stale inbox
  offers. Expiry does not strand cleanup; old credentials cannot resurrect work.
- Controller/runtime death after land, during shutdown, and after tab removal
  but before recording it converges without repeat land, respawn or
  wrong-target close. Timeout/ambiguous ownership preserves visible cleanup
  work and the land report.
- Reused session/tab/PID identities, rearranged tabs and unrelated panes
  refuse closure. Preserve Controller, shared session, worktrees, commits,
  Outputs, logs and pi history. Human holds never permit force-killing.
- Migration preserves a populated Exp 1 Board copy and lifecycle obligations;
  historical fixtures/binaries stay unchanged while the new kernel is tested.

2. Review: `Process.run_bounded` check operation with retained evidence, plus
