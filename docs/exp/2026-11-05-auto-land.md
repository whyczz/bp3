# Exp 2 — Auto-land implementation contract

Status: proposed implementation packet; not an implemented guarantee.
Governing scope: [MVP Quest, Exp 2](../quests/2026-11-05-bp3-mvp.md).
Genesis evidence: [Exp 1 record](2026-11-05-genesis.md). No master promotion or push authority.

## TL;DR

A fresh reviewer and an independent check must approve the exact commit that
moves the Quest branch. For Exp 2, integration is **fast-forward only**, from the
frozen base: do not introduce merges, cherry-picks, or automatic rebases. Journal
intent before the compare-and-swap ref update; recover the Board afterward.
Rejected reviews create rework on the same exp, never overwrite old evidence.
After finalized landing, the runtime automatically retires the exp's Worker
sessions and closes their owned tabs. Human takeover holds closure until the
existing `/bp3-release` handoff; ordinary completion needs no human close command.

## ELI5

The author submits a sealed parcel. Someone else inspects it; a separate test
run checks it. Only that parcel can go onto the Quest shelf, and only if nobody
has moved the shelf since we checked. A receipt says exactly what landed and
how to undo it. The finished Workers leave the workspace, but their work and
receipts stay. If you are using a Worker, it waits until you hand it back with
`/bp3-release`. Master is a different shelf, still requiring the human's approval.

## Context and bootstrap boundary

Current `Workflow.report` stores a candidate, not approval. `Authority.allowed`
has Controller/Worker/Bridge/Runtime permissions but no verifier/reviewer role.
`Execution_ops.reserve` permits only generation zero, and `Store.schema` has one
live-author slot. `Launcher.launch` refuses unrecorded target movement. These
are intentional genesis limits, not APIs to bypass with direct SQL or Git.

The original bootstrap split put skill fix `28a274a` on `master` (pushed) and
Exp 1 `ab9f0d1` on `quest/bp3-mvp` (local only). The user subsequently requested
local checkpoints of the post-Exp 1 workspace additions, dated exp records,
writer skill and this expanded plan, leaving a clean implementation baseline.
These checkpoints are not auto-land, master promotion or push authorization.

Keep the old bootstrap Board as historical provenance. After checkpointing,
record the exact clean Quest commit containing the workspace and docs changes,
and explicitly establish a fresh implementation Board at that commit. Do not
silently rewrite an existing Board's frozen base to match a hand-moved branch
or launch from the older genesis commit while assuming later additions exist.
The recorded SHA, not a moving branch name or dirty checkout, is the next
implementation Worker's baseline.

Exp 2 kernel work is delegated through the existing genesis runtime to a Worker
on that committed baseline. That runtime stays frozen; the candidate kernel
is tested on Board copies and fresh toy repos. Do not hot-swap the coordinator
executing the implementation exp. The toy auto-land proof is separate from
accepting/activating the kernel that implements it.

## Architecture and data

```text
frozen author brief -> author execution -> immutable candidate
                                           |
                           independent verifier + fresh reviewer
                                           |
                            exact gates + journal reservation
                                           |
                            Git compare-and-swap Quest ref
                                           |
                         durable land report / recoverable journal
                                           |
                           durable per-execution close requests
                                           |
                         runtime shutdown + owned-tab cleanup
```

The existing standard/code-only, single-host, cooperative trust model remains.
One author and one reviewer maximum, sequential is sufficient. No general DAG,
lanes, external push, master promotion, production sandbox, or autonomous rebase.

Required additions (names may be refined in the Worker design, invariants may not):

- **Execution role** `author` or `reviewer`, from Runtime reservation, not a
  caller-controlled report field. A reviewer binds to one exact candidate and
  must have a different pi session/execution/worktree from the author.
- **Execution terminal state:** reporting seals an author candidate and ends its
  author lease without discarding evidence. Review completion similarly ends
  the reviewer lease. A late heartbeat must not restart a sealed execution.
  Sealing authoring/review authority is distinct from closing its visible session;
  a narrow authenticated lifecycle channel remains until cleanup completes.
- **Verification receipt:** candidate ID, exact commit/base, frozen check argv,
  independent workspace identity, exit status, retained stdout/stderr, clean
  tree observation and time. Worker prose is never a verification receipt.
- **Review receipt:** candidate ID + exact commit/base, reviewer execution,
  accept/reject, findings and evidence. The author credential cannot write it.
- **Integration intent:** stable operation/intent ID, exp, selected candidate,
  exact before/after ref, target ref, bound verifier/reviewer receipts, and
  progress (`prepared`, `applied`, `finalized`, or `incident`).
- **Land report:** exactly one per successful integration, TL;DR, IIUC, demos,
  tests, code pointers and revert handle. Retained after rework or revert.
- **Close request:** stable ID bound to the finalized land and exact execution,
  generation and endpoint identity; retained progress/reason for pending,
  held-by-human, closing, closed or incident. Bound per-execution interaction
  revision prevents an old release or shutdown acknowledgement from overriding
  newer takeover. Names may change; request identity and retry semantics may not.
- **Rework:** selected candidate/review disposition and explicit reason retained;
  same exp, new author ownership generation/execution, old evidence immutable.
  A rejected or obsolete candidate cannot become selected via receipt replay.
- **Incident:** actual/expected target, intent if any, reason and blocked state.
  Target movement without a matching intent freezes integration, never becomes
  the new base just because a retry saw it.

Author ownership generation and reviewer identity must not fight over the
current `UNIQUE(exp_id,generation)` constraint. Specify the migration and
per-role/current-selection constraints before adding another launcher shape.
Do not increment the author's generation merely to start its reviewer.

## Operations and authority

1. **Prepare/verify candidate.** Read the sealed result and immutable brief,
   ensure target equals its frozen base, and create an independent worktree at
   the exact candidate. Run check argv directly (no shell interpolation),
   outside SQLite transactions, with a bounded deadline. Capture output outside
   the candidate. Require the committed/tracked tree and HEAD to remain exact;
   reject tracked or untracked source changes. Build artifacts may be ignored.
   Persist success or failure honestly. No receipt on interrupted execution.
2. **Start reviewer.** Runtime reserves a reviewer tied to that candidate and
   launches a fresh pi session/worktree. Give it the frozen brief, exact diff,
   and verifier evidence; require findings and accept/reject through Board ops.
   No author-role token can manufacture review approval.
3. **Rework.** Reviewer rejection returns the exp to rework/working on the same
   identity. A new author execution consumes the rejected candidate/findings;
   generation fences its predecessor. Scope/check changes need explicit recorded
   amendments, not reinterpretation of free-text steering. Exp 2's happy-path
   fixture uses an existing concrete `dune runtest --root .` check; do not parse
   the Exp 1 human answer's prose into an executable gate.
4. **Auto-land.** Deterministic runtime action after both gates, not an author
   command or another human scheduling step. Revalidate selected generation,
   candidate/base/check/reviewer bindings, budget/cancel/takeover/permission,
   absence of unresolved questions, and target identity. Record an exclusive
   integration intent before touching Git. Never land to master or a non-Quest
   ref. Refuse a target checked out in any worktree, rather than silently
   invalidating that worktree's index.
5. **Apply/reconcile.** `git update-ref TARGET AFTER BEFORE` is the only target
   mutation for land. Transactionally finalize the exp as `auto_landed`, update
   the recorded Quest head, and insert exactly one land report/event/receipt
   plus close requests for its owned author/reviewer executions in the same
   transaction. The runtime performs cleanup afterward, never inside that
   transaction. No SQLite transaction spans a process call. Restart with a
   prepared intent: if actual ref is BEFORE, recheck gates and retry the CAS; if AFTER, finish the
   recorded action once; if neither, freeze as an incident. An AFTER ref without
   a matching durable intent is not evidence of authorized landing.
6. **Revert.** Controller may explicitly request a revert of an auto-land on
   the Quest branch. Create a **new revert commit**, not a reset or history
   rewrite, in an owned worktree; journal and CAS against the exact current
   head. Reject conflicts/moved targets rather than choosing resolutions. Mark
   reverted disposition and retain the original land report plus the revert
   receipt. The fixture deliberately returns to its failing baseline; a revert
   is recorded as an undo, not a newly accepted feature with invented green
   checks. Master rollback/build activation remains Exp 3.

A live Controller dying does not make it the owner of a new execution. A fresh
Controller reads existing obligations and lets the runtime resume only the
journaled action. The same stable operation ID replays the same result; reuse
with changed input is a conflict. Report receipts and execution authority remain
separate, including bridge cached-offer fencing from genesis.

## Post-land Worker retirement and human release

**Policy owner:** control-plane/Board operations decide eligibility and persist
intent; the runtime reconciles shutdown and terminal removal without a model
call or a live Controller. The existing pi bridge may execute graceful shutdown
and protect its local interaction boundary. No separate extension infers completion.

### Trigger and authority

- Trigger only on finalized, recorded exp-to-Quest landing, not report, idle,
  successful Git invocation alone, or Quest-to-master promotion. Working,
  blocked and awaiting-review Workers are not closed by this success policy.
- Seal work authority at report/review completion; preserve the lifecycle-only
  channel for presence, settled, takeover/release and shutdown acknowledgement.
  Current `Board.dispatch` uses `Authority.live` for all bridge signals, so this
  requires an explicit authority change: do not keep `desired=run` merely to
  receive release, and do not restore work authority to permit cleanup.
  Expired work budgets must not prevent authenticated retirement or grant more
  model work. Closed/obsolete credentials cannot deliver work or resurrect an
  execution through heartbeat, cached inbox offer or release replay.
- Close requests cover the landed exp's owned Worker executions, including any
  superseded attempts still present, not other exps or the Controller. Preserve
  candidates, worktrees, branches, Board history and pi session files. Successful
  retirement is not `cancel`: it must not turn the landed exp into `cancelled`.
  Cancellation/abandonment cleanup is a separate explicit disposition; do not
  fabricate landing to collect failed or legacy Exp 1 sessions.

### Human handoff: reuse `/bp3-release`

The command already emits an authenticated `release` signal and requires idle.
Use that protocol, never terminal scraping or matching a command in prose:

1. With no takeover, finalized land can close a safely settled Worker without
   asking for `/bp3-release`. A release before land remains sufficient unless
   a later interaction takes over again; no new post-land approval ceremony.
2. Interactive input/user shell activity latches takeover. A landed Worker under
   takeover stays open with an inspectable reason: waiting for `/bp3-release`.
3. Accepted release clears only that execution's current takeover. It does not
   prove landing, resolve questions, clear permission prompts, or authorize new
   work on a sealed execution. Closure additionally requires settled-idle, no
   pending messages/obligations and no permission prompt; unresolved obligations
   need an explicit recorded disposition, not silent deletion.
4. Bind release and close authorization to the current execution/session and a
   monotonic interaction revision, checked both by the Board and local bridge.
   New interaction invalidates earlier release/close eligibility. A delayed
   release response must not clear a newer local takeover latch; cached success
   is an acknowledgement of the old operation, not fresh permission to close.
5. Recheck local idle, pending input, takeover and permission at the shutdown
   boundary, not just on an earlier heartbeat. Serialize that boundary with
   input handling: activity arriving before shutdown is committed holds closure;
   after commitment the session is closing and cannot accept new work. Runtime
   must not bypass a withheld shutdown handoff by blindly killing the tab.

### Recoverable, scoped cleanup

Persist the close intent before external action. Revalidate the exact owned
session incarnation and pane/process identity; a stored PID or reusable tab ID
alone is insufficient. Request graceful pi shutdown with a bounded wait, then
remove the owned Worker terminal/tab using explicit IDs, never the focused tab.
If a tab now contains unrelated terminals, do not close it wholesale. Keep the
Controller, shared Zellij session and Ghostty window open. An empty terminal is
not proof that the Worker process or its owned children exited; record only what
was observed, with unsupported descendant cleanup stated rather than assumed.

Runtime restart resumes pending requests without respawn. If the exact target is
already gone, reconcile that fact; if identity is ambiguous or shutdown times
out, retain a visible cleanup incident, not guessed closure or force-killing an
unrelated process. Human-held state remains an explicit hold, not a timeout that
authorizes a kill. A cleanup failure leaves the exp landed and report intact:
never undo Git, repeat land, or lose the request merely because UI cleanup failed.

## Storage, migration, and compatibility

Schema v1 is explicitly checked in `Store.open_db`. Add a named v1-to-v2
migration, never silently migrate while an old runtime is attached. Acquire
exclusive runtime ownership and take a consistent backup first. Preserve all
old rows, frozen briefs, receipts, event cursors, and terminal obligations.
Retain schema v1 Boards as genesis evidence. Test migration on copies; the
running genesis runtime continues using its original v1 Board/binary/bridge.
Older binaries must fail closed on the new schema, not interpret new states.

The integration journal bridges SQLite and Git; a SQLite backup alone is still
not a portable artifact backup. No claim of full restore until rehearsed.
Independent worktrees are evidence isolation from accidental author changes,
not a hostile-code security boundary.

## Acceptance checks

All currently fail by absence of implementation; none are claimed passed.

- Fresh author/reviewer identities; author cannot approve itself or supply a
  successful verification receipt. Review binds to the exact candidate.
- Independent check failure produces no target movement, no land report and no
  `auto_landed`, even when Worker evidence says the check passed.
- Hand-moved target creates an incident and remains untouched; do not silently
  rebase the brief or auto-retry against the new head.
- Reviewer rejection yields rework on the **same exp**, with a fresh author
  generation; obsolete reports/reviews cannot resurrect the rejected result.
- Happy path on a fresh toy repo: exact independently checked/reviewed candidate
  auto-lands once, emits the compact stored report, and names a working revert
  handle. Its owned author/reviewer processes and tabs then close automatically;
  the Controller and evidence remain. No master movement, push or extra
  scheduling/close approval.
- Duplicate/concurrent land requests and runtime death before/after ref CAS
  yield exactly one landing/report or a visible incident, never guessed success.
- Cancellation/takeover/budget/permission, unresolved question, changed
  verification workspace, mismatched receipt and checked-out target all refuse.
- Revert produces a new commit, restores the baseline tree, keeps both receipts,
  and refuses target movement or integration conflicts.
- Reported, blocked and awaiting-review Workers do not close before finalized
  land. A release without land never triggers successful-retirement cleanup.
- Human interaction after land holds closure; `/bp3-release` at settled-idle
  permits it once other gates clear. No takeover means no release is required;
  release before land does not need repeating absent renewed interaction.
- Busy release is refused. Permission prompts, queued input and unresolved
  obligations still block closure after release; newer interaction defeats an
  in-flight release response, cached receipt or close authorization. Exercise
  this with delayed acknowledgements at the local bridge and Board boundaries.
- Sealed Workers can report lifecycle/release/shutdown facts but cannot report
  new work, receive stale inbox offers or reacquire a work lease. Expired work
  budgets do not strand lifecycle-only cleanup or extend model authorization.
- Controller/runtime death after land, during shutdown, and after tab removal
  but before receipt persistence converges without duplicate land, respawn or
  wrong-target closure. Shutdown timeout/ambiguous identity records cleanup
  pending or incident without undoing landing or dropping evidence.
- Reused session/tab/PID identities, rearranged tabs and unrelated panes are
  refused as closure targets. Preserve the Controller, shared session, worktrees,
  commits, results, logs and pi session history through successful cleanup.
- Schema migration preserves a copy of the populated Exp 1 Board, including
  lifecycle/cleanup compatibility; old running binaries/fixtures remain
  unchanged throughout candidate testing.

## Delivery slices within Exp 2

1. Roles, separate work/lifecycle authority, terminal/rework transitions,
   close-request state and schema migration with counterexample tests — start
   from an exact recorded source checkpoint with a fresh Board, not the
   historical pre-genesis Board. Account for the workspace follow-up's source
   disposition before delegation; never silently substitute a dirty checkout.
2. Independent verifier and fresh reviewer with reject/rework proof.
3. Journaled auto-land, report, crash/refusal drills and explicit revert.
4. Runtime-owned post-land cleanup, `/bp3-release` interaction/replay race drills,
   bounded shutdown and exact-target reconciliation after restart.
5. Live toy rehearsal + read-only adversarial review of the result, including
   automatic closure and human takeover/release while preserving the Controller.
   Only then begin Exp 3's promotion/activation design and Worker-built context
   briefing.

## Red-chair record and open decisions

- **Input:** the user observed a finished Worker, not an approved/landed result.
  Keep the verified candidate and Exp 1 completion separate from Exp 2 claims.
- **Problem:** a happy-path merge command would not establish independent
  approval or survive the Git/SQLite boundary. Existing Board authority and
  one-generation constraints must change explicitly, not via test-only SQL.
- **Solution:** merging after reviewing the author SHA could land a different
  tree. The cheapest sound boundary is exact fast-forward integration with
  independently checked/reviewed candidate SHA and expected target CAS. A
  future need for composition would require a new exact-integration contract.
- **Historical checkpoint risk:** before `ab9f0d1`, launching from HEAD would
  have omitted the genesis kernel and one mixed commit would have absorbed the
  independent installer fix. The bootstrap split resolved that. The current
  handoff also checkpoints the workspace/docs follow-up before freezing the
  next implementation base. This is not a recurring human scheduling gate.
- **Post-land cleanup (user-approved scope):** completion is a durable land,
  not a quiet terminal. Separate sealed work authority from visible session
  lifetime; otherwise the bridge is fenced before it can receive cleanup.
  Reuse `/bp3-release` rather than add a routine human close step. The strongest
  race is a new interaction while an old release/close response is in flight;
  bind to interaction revision and guard the local shutdown boundary. Runtime
  owns recovery; ambiguous ownership is an incident, never a guessed kill.

Owners: implementer resolves concrete schema/API names and bounded process
supervision; Controller reviews their invariants before build. Human owns the
authorized source-checkpoint split and eventual Quest-to-master comprehension
approval, not ordinary Exp 2 scheduling. Cost accounting and UI notification
presentation remain explicit limitations; the stored report must still exist.
