# Exp 1 — Genesis: design, code tour, and evidence

TL;DR
A durable Board-to-visible-Worker loop now exists: frozen brief, blocker/reply,
immutable candidate, and recovery after process death. It does not approve,
land, promote or push the candidate.

ELI5
The Worker gets its own workspace and window. The Board remembers what it was
asked, what it needs, and what it produced, even if the Controller disappears.

## Mini-design and implementation contract

This section consolidates the former `bp3-genesis-contract.md`. It resolves the
Exp 1 subset of the [MVP architecture](../designs/bp3-control-mvp.md), not the
future review/landing/promotion design. The accepted source baseline is
`ab9f0d1`; later UI follow-ups must not inherit its acceptance evidence blindly.

### Shape

```text
Controller session -- CLI op/context --> Board operations --> SQLite
        |
        +-- CLI launch --> runtime --> Zellij / pi Worker
                              ^                |
                              +-- pi bridge ---+  lifecycle + inbox
                                               |
                             Board <-- CLI op -+  blocker / report
```

The Controller is the live decision-making session, not an autonomous planner
inside `core/control/`. The runtime waits deterministically; no model is needed
to poll for heartbeats, and no pane text is read to classify Worker state.

### Data and storage

`Store.schema` has eight tables: `quests`, `exps`, `executions`, `results`,
`questions`, `inbox`, `receipts`, `events`. An exp is the assignment; an execution
is the attempt. Its frozen brief contains objective, acceptance, scope,
non-goals, check argv and a 1–86400-second budget. Execution adds worktree,
branch, generation, token, endpoint and deadline. One immutable result binds
an exact commit and Worker evidence to that execution/brief.

Exp states are `working -> blocked -> working -> ready`, with explicit
cancellation. Execution desired state, liveness, ready/idle, permission and
human takeover are separate facts. Exp `ready` means candidate reported;
execution `ready` means bridge handshake. Neither is review or land approval.

`Store.transaction` uses short `BEGIN IMMEDIATE` transactions with foreign keys
and a busy timeout; state, event and receipt commit together. The tables hold
current state, not projections rebuilt by replaying the event log. Schema v1
fails closed on unsupported versions. One read transaction keeps `context` and
its event cursor consistent; execution tokens are omitted. SQLite backup uses
the online backup API into a new file, not an overwrite or portable Git backup.

### Protocol, authority, and retry

`Packet.canonical` sorts JSON keys and rejects duplicates. IDs are bounded ASCII
slugs; v1 operations carry a stable operation ID, operation and payload.
`Authority.allowed` separates Controller, Worker, Bridge and Runtime calls.
Worker/bridge requests carry execution ID, generation and a random local token.
`live` checks current ownership/run intent/deadline; `autonomous` checks takeover
and permission. This is cooperative fencing, not hostile-process isolation.
Only standard/code work and one live author are admitted; unsupported lanes and
prerequisites are rejected, not ignored.

`Board.apply` authenticates, looks for a receipt, performs Git preflight outside
the transaction, then checks the receipt again inside the transaction before
mutation. Exact retries return the stored response; changed payload under the
same operation ID fails. Old Worker report success can be acknowledged after
cancellation, but new obsolete mutations cannot. Cached bridge offers are
stricter: replay revalidates live authority/session and offer eligibility,
because an old offer could start new work. No transaction encloses Git, process
launch or a model call.

### Workflow and delivery

`Workflow` owns create/brief/block/steer/answer-handled/report/cancel. No function
there launches a process. Questions retain IIUC, challenged next step,
recommendation, answer and handling. Cancelling does not erase obligations.
`report` requires no unresolved question and nonempty evidence. Git preflight
requires exact full SHA = workspace HEAD, a clean worktree, and ancestry from
the frozen base. That establishes candidate identity, not check success, scope
compliance or an independent verification receipt.

`Execution_ops.next_delivery` moves inbox messages through
`queued -> offered -> observed -> handled`. A new poll cannot blindly re-offer
an ambiguous message; the identical poll can replay its offer only while still
authorized. The pi input hook proves observation; explicit Worker
`answer-handled` proves handling. Settled-idle or a transport ACK cannot do so.
An offer racing takeover/prompt can remain ambiguous: no forced reinjection or
exactly-once external-delivery promise exists in genesis.

### Launch, runtime, and adapter

`Launcher.launch` reserves ownership before side effects, journals worktree
creation and spawn intent, and returns an existing reservation on retry rather
than guessing whether another Worker should be spawned. Incomplete stages need
explicit recovery. Capabilities live in a mode-0600 launch file, not inspectable
Zellij argv. The bridge's actual session/pane/PID/worktree handshake determines
readiness; no brief is dispatched merely because a process was started.

`Runtime.serve` holds an OS singleton lock and private Unix socket. Death
releases the lock; cleanup unlinks the socket before unlocking. Every two
seconds it reconciles signals; missing heartbeats become stale after about ten
seconds, without fabricated exp failure or replacement. Budget exhaustion
fences work without signaling a stored PID that might have been reused.
`Transport` bounds incoming JSON frames and uses connection/read timeouts.
`Process.run` still performs synchronous external commands without deadlines.

The TypeScript bridge maps documented pi events to signals and inbox offers to
`sendUserMessage(..., followUp)`. Only `agent_settled` plus `isIdle()` proves
final idle, not `agent_end`. Interactive input/user shell actions latch
takeover; UI prompt hooks track permission. Local latches protect the gap
before Board signals. Transport failures retry the same envelope; protocol
failures stop delivery and request abort. Session switch/fork/tree changes are
blocked; the original pi session identity fences replacement sessions. A
runtime restart accepts the same living Worker's heartbeats, not a new spawn.
The fixture freezes the binary/bridge; this is not yet promotion machinery.

## Code map and invariants

| Path | Responsibility |
|---|---|
| `core/protocol/packet.ml` | v1 JSON, canonical retry identity, brief validation, local capabilities |
| `core/board/store.ml` | schema, prepared SQL, short transactions, snapshots/events |
| `core/board/authority.ml` | caller permissions, execution ownership, budget/takeover fences |
| `core/board/board.ml` | authenticate/replay/preflight/transaction boundary |
| `core/board/workflow.ml` | Quest, exp, brief, blocker, answer handling, candidate |
| `core/board/execution_ops.ml` | launch journal, bridge observations, durable inbox offers |
| `core/runtime/` | bounded private socket, singleton runtime, worktree/pane launcher |
| `core/control/main.ml` | disposable CLI, JSON context and operation ingress |
| `plugins/harness-pi/bridge.ts` | pi lifecycle hooks and transport, no policy or pane parsing |
| `tests/test_genesis.ml` | isolated Boards/Git repos, rollback/fencing/retry/process counterexamples |
| `tests/bridge.test.mjs` | held-ready, same-request retries, follow-up/ACK, takeover/release, abort |
| `tests/controller-recovery.mjs` | opt-in paid test: real Controller SIGKILL/replacement during work and pending question |

The implementation contract above governs Exp 1; there is no separate live
contract/runbook copy to keep in sync.
Comments at the boundaries explain why an idle signal is not a result, an offer
is not handling, a report is not approval, and a launch retry must not respawn.
No function named land/review/promote is stubbed to succeed.

## Create a live fixture

This starts a visible real pi process. The brief is **held** until explicitly
queued; queueing it authorizes model work and may incur provider charges.
Choose a new directory and a dedicated Zellij session name each time.

```sh
tests/start-toy .bp3/my-run bp3-my-run YOUR_PROVIDER/MODEL hello
# Or use `blocker` instead of `hello` for the missing-check human drill.
zellij attach bp3-my-run
```

The script prints the exact context and queue-brief commands. It freezes the
bootstrap binary/bridge under that fixture's `genesis/`, materializes a fresh
Git repository from `tests/toy-template/`, creates `quest/toy`, starts one
runtime, and launches one Worker. `hello.ml` deliberately fails its check at
baseline. Scope is `hello.ml` only; the Worker must not alter the harness.
Use `dune runtest --root .` in nested toy worktrees so Dune does not select the
parent bp3 project.

Every mutation is a v1 envelope with a stable `op_id`, `op`, and `payload`, fed
to `bp3 --board PATH op FILE` (or `op -`). Controller operations are
`quest-create`, `exp-create`, `brief`, `steer`, `cancel`. Worker operations are
`block`, `answer-handled`, `report`, with credentials supplied from the Worker
environment. Reuse an operation ID only for the exact same request. Public
context excludes capabilities; do not publish the Board database, launch file,
or raw receipts, which contain local credentials.

## Recovery, ownership, and known limits

- `.bp3/board.sqlite` is the **historical bootstrap Board**, recording the real
  home Quest `bp3-mvp` and genesis exp at pre-genesis base
  `2c8bce6b68073c89d62f6c0402585316b19e94aa`. The user-authorized source checkpoint
  now advances `quest/bp3-mvp`; do not launch against the historical Board or
  silently rewrite its frozen base. Before Exp 2, preserve it and initialize a
  fresh implementation Board at the exact Quest checkpoint via normal create
  operations. The historical bootstrap exp remains `working` in this minimal
  schema (no administrative bootstrap-accept op). Completed observations are
  recorded here, not as a fabricated Worker result or a bypassed auto-land.
- `context` is a machine JSON snapshot, not yet the Exp 3 human briefing.
  Toy Boards are separate authority domains; do not copy their candidates
  into the home Board as fictitious bp3 results.
- Restart with the **same frozen** binary, Board and bridge:
  `.../genesis/bp3 --board .../board.sqlite runtime --binary /absolute/.../genesis/bp3 --bridge /absolute/.../genesis/bridge.ts`.
  Do not repeat an ambiguous launch to force a spawn. Its durable stage is the
  recovery evidence; new generation/rework recovery is not implemented yet.
- For a clean stop, obtain the current runtime PID with `ping`, then SIGTERM
  that owned process. Close only the owned Zellij pane/session. Keep the Board,
  worktrees, launch files and sessions while evidence is needed. A stopped
  runtime does not kill the Worker; a `cancel` fences but does not OS-kill it.
- An offered-but-unobserved message may be ambiguous after process loss or a
  takeover race. Genesis does not promise exactly-once external delivery or
  provide a forced reinjection command. Inspect and stop rather than guess.
- One live author, standard/code only, no prerequisites/review/land/promotion.
  A reported execution still occupies the author slot until explicit cancel
  or expiry; terminal/rework transitions belong to Exp 2, not implicit respawn.
- Synchronous Git/Zellij launch has no external-command deadline; a hung
  command can delay the event loop. Receipt/event compaction, portable restore,
  cost measurement, longer idle-provider observation, and process-tree
  supervision remain hardening work. Worktrees/capabilities are not isolation.
